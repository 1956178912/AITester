# LLM 配置批次验证冒烟（2026-10-14，DeepSeek 官方文档对齐）

> 背景：EMSE 批次日志出现大量"执行失败/重试/超时"字样，按 DeepSeek 官方
> 文档 + 实际日志归因后配置 LLM。**关键归因**：日志中占绝大多数的
> "第 N 次执行失败，尝试重试"是**执行器对 pytest 变红的重试**——测试在
> 缺陷代码上非零退出即**检测信号本身**（检测到缺陷的正常路径），非故障；
> `执行超时（>30s）`是测试侧挂起保护（挂起测试 × 30s 上限）；API 侧
> 零 429/连接错误签名。真正的 LLM 侧缺陷是结构化输出解析失败
> （`M10：LLM 未输出 logic_analysis`、`llm_json_parse_failed`）。

## 本批次配置（三项，均按官方文档）

1. **JSON Output（LLM_JSON_MODE，默认 on）**：`response_format=
   {"type":"json_object"}` 绑定到 6 处 JSON 契约调用点（Planner 测试计划、
   Debugger 补丁/严格重试/批评者/缺陷分类）。官方前置条件（提示须含
   "JSON" 与格式示例）已逐一核查满足；官方已知"偶发空响应"由既有
   空响应重试承接。`LLM_JSON_MODE=off` 供旧批次逐字节复现。
2. **数值表达式 JSON 修复**（`src/utils/helpers.py`）：LLM 在 JSON 值位置写
   Python 数值表达式（`10**18`、`10**18+1`、`10_000`）——JSON 非法，且
   既有修复链不含数值路径 → 解析失败后叶子回退**静默返回错误片段**
   （`{'items': ...}`）→ 被误诊为 M10。现以受限求值（无 eval，指数有界，
   字符串内防护）换算为等值 JSON 数字。
3. **finish_reason 守卫**：`length`（max_tokens 截断）/`insufficient_system_
   resource`（推理资源中断）视为可恢复失败重试，不把残缺内容交给下游。

## 验证证据（本目录）

- 本冒烟（seed45 前 3 任务，干净口径，新命名空间）：
  **M10=0 / Planner 结构不完整=0**，3/3 任务产出完整计划（各 9 用例）；
- 修复前同任务（`emse_jsonmode_smoke_v2_20261014`）：task_0000 回退默认
  计划（M10=1）——根因 = `10**18+1` 数值表达式致解析失败；
- 缓存真实样本回归：9/9 条历史 Planner 响应（含 `10**18`、`10**18+1`
  与双对象背靠背两类失败形态）经修复后完整提取。

**口径披露**：LLM_JSON_MODE 改变结构化调用的采样约束（默认 on）——
未来批次 provenance 记录 `LLM_JSON_MODE`（已入 `_env_snapshot_keys`）；
复现本批次前历史需显式 `LLM_JSON_MODE=off`（数值修复为纯语法层、
对历史请求无影响，无需开关）。数值修复属**解析层**改进：历史批次的
原始响应在新代码下解析更完整，但已入库工件不受影响。

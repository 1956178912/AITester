# 2. 相关工作

## 2.1 基于 LLM 的测试生成

早期工作直接将 LLM 应用于单元测试生成。**UnitGen**（Zhang et al., 2023）利用 LLM 根据函数签名生成测试骨架，但未处理测试失败后的修复问题。**TestGenie**（Qu et al., 2023）基于 LLM 的代码补全能力进行测试生成，缺乏系统化的规划步骤，生成的测试用例逻辑覆盖不完整。**DiffBlue Copilot** 为商业闭源工具，无公开实验数据可供对比。

与上述工作不同，AITester 引入了显式的逻辑规划阶段，将测试生成从"一次调用"升级为"规划→生成→执行→修复"的迭代闭环。

## 2.2 多智能体协作与自我修复

**AutoGPT**（Su et al., 2023）提出通用多智能体框架，但缺乏针对软件测试领域的专业化设计。**SWE-Agent**（Yang et al., 2024）面向 SWE-bench 的代码修复任务，以问题修复为目标而非测试生成。**AgentCoder**（Wang et al., 2024）实现多智能体代码生成，但测试覆盖完整性未充分验证。

AITester 的独特之处在于：将测试生成与代码修复统一在同一多智能体框架中，通过 Planner-Generator-Executor-Debugger 的流水线协作，实现端到端的测试创建与问题修复。

## 2.3 错误分类与修复策略

**DeepFix**（Gupta et al., 2017）基于神经网络进行 bug 修复，需要大量训练数据且泛化能力受限。**TBar**（Xiong et al., 2020）采用模板-based 测试修复方法，不适用于 Python 的动态特性。

AITester 首次将错误分类与分层修复策略集成到多智能体工作流中，通过规则匹配实现 $O(1)$ 错误分类，再以针对性策略指导 LLM 修复，避免了通用修复方法中"试错成本高"的问题。

## 2.4 检索增强生成在软件工程中的应用

RAG 技术已在代码补全（e.g., **CodeRAG**）、文档检索等场景中得到验证。AITester 借鉴这一思路，在 Generator 和 Debugger 阶段引入 ChromaDB 向量检索，利用历史成功测试用例与修复补丁作为参考，进一步提升生成质量。
